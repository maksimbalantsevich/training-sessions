# Requirements: Training Sessions Workspace

- **Task ID:** `training-sessions`
- **Source:** [TASK.md](./TASK.md)
- **Status:** Ready for planning — блокирующие вопросы закрыты (D-1…D-4)

## 1. Цель

Тренер открывает рабочее пространство, видит список тренировочных сессий из мок-API, фильтрует его по одному статусу и создаёт новую сессию (название + будущие дата/время), которая сразу появляется в списке. Задача учебная: объём продукта и техники намеренно минимален.

## 2. Факты о репозитории (проверено)

| Факт | Источник |
|---|---|
| React 19 + TypeScript + Vite | `package.json`, `vite.config.ts` |
| Пакетный менеджер — npm | `package-lock.json` |
| Скрипты: `dev`, `build`, `lint` (oxlint), `test` (`vitest run`) | `package.json` |

| Living specs (`specs/`) отсутствуют | файловая система |

## 3. Пользователь и сценарий

- **Пользователь:** тренер.
- **Основной сценарий:**
  1. Открывает приложение → видит сессии, загруженные из мок-API.
  2. Выбирает фильтр по статусу (или `All`).
  3. Открывает форму создания.
  4. Вводит название и будущие дату/время, отправляет.
  5. Видит созданную сессию в списке.

## 4. Критерии приёмки

### AC-1. Загрузка и отображение списка
- **AC-1.1** При открытии приложения выполняется запрос списка сессий через заменяемую границу запросов (HTTP-клиент или эквивалент), а не через импорт мок-данных в UI.
- **AC-1.2** Пока запрос выполняется, отображается состояние загрузки.
- **AC-1.3** После успешной загрузки для каждой сессии видны: название, статус, дата и время начала.
- **AC-1.4** При ошибке запроса отображается одно понятное пользователю сообщение об ошибке (без технических деталей/stack trace).
- **AC-1.5** Ошибка восстановима: пользователь может повторить загрузку (например, кнопкой «Повторить») без перезагрузки страницы, и при успешном повторе отображается список.

### AC-2. Фильтр по статусу
- **AC-2.1** Доступны ровно два варианта фильтра: `All` и `Scheduled` (D-1).
- **AC-2.2** По умолчанию выбран `All`, отображаются все загруженные сессии всех статусов (`scheduled`, `completed`, `cancelled`).
- **AC-2.3** При выборе `Scheduled` отображаются только сессии со статусом `scheduled`; сессии `completed` и `cancelled` скрыты.
- **AC-2.4** При возврате на `All` снова отображаются все сессии, включая созданные в текущей сессии работы.
- **AC-2.5** Текущий выбранный вариант фильтра визуально и программно (доступно для assistive tech / тестов) различим.

### AC-3. Форма создания
- **AC-3.1** Пользователь может открыть форму создания из рабочего пространства.
- **AC-3.2** Поля формы: только название и дата/время начала. Поля выбора статуса нет (D-2).
- **AC-3.3** Название обрезается по краям (trim) перед проверкой; допустимая длина после trim — от 3 до 80 символов включительно.
- **AC-3.4** Дата и время обязательны и должны быть строго в будущем относительно момента отправки.
- **AC-3.5** При нарушении любого правила отправка не выполняется и показывается полезное сообщение валидации, указывающее, что исправить (например, «Название должно содержать от 3 до 80 символов», «Укажите дату и время в будущем»).
- **AC-3.6** Пока запрос создания выполняется, повторная отправка невозможна (кнопка заблокирована и/или повторный submit игнорируется); на мок-API уходит ровно один запрос.
- **AC-3.7** Отправляется название уже после trim.

### AC-4. Результат создания
- **AC-4.1** После успешного ответа созданная сессия появляется в видимом списке без перезагрузки страницы.
- **AC-4.2** Созданная сессия отображается с теми же полями, что и остальные (название, статус, дата/время).
- **AC-4.3** Статус созданной сессии — `scheduled`. Его выставляет мок-API, клиент статус не отправляет (D-2).
- **AC-4.4** Созданная сессия видна при обоих вариантах фильтра — `All` и `Scheduled`, в том числе если форма отправлена при активном `Scheduled` (D-3).

### AC-5. Граница моков
- **AC-5.1** Мок-данные и обработчики находятся за HTTP-границей; UI-компоненты не импортируют мок-данные напрямую.
- **AC-5.2** Поскольку механизма моков в репозитории нет, используется MSW или другой общепринятый HTTP-мок (решение — за `architect`/`api-integration`, см. OQ-7).
- **AC-5.3** Реальный backend-сервис не реализуется.
- **AC-5.4** Мок обслуживает как минимум: получение списка и создание сессии; есть способ воспроизвести ошибку списка (для AC-1.4/1.5 — в тесте и/или вручную).
- **AC-5.5** Исходные мок-данные содержат минимум по одной сессии каждого статуса: `scheduled`, `completed`, `cancelled` (D-4), чтобы фильтр `Scheduled` давал видимый эффект.
- **AC-5.6** Ответ мока на создание содержит сессию со статусом `scheduled` независимо от тела запроса (D-2).

### AC-6. Автотест
- **AC-6.1** Добавлен минимум один поведенческий тест (Vitest + Testing Library + user-event) основного сценария: фильтрация **или** успешное создание.
- **AC-6.2** Тест взаимодействует через UI (роли/тексты), а не через внутреннее состояние компонентов, и проходит через ту же мок-границу.
- **AC-6.3** `npm test`, `npm run lint`, `npm run build` проходят. Существующий smoke-тест либо продолжает проходить, либо осознанно обновлён под новый UI (см. OQ-9).

### AC-7. Ручная проверка
- **AC-7.1** Приложение запущено (`npm run dev`), в браузере один раз пройдены: загрузка списка, фильтр, создание.
- **AC-7.2** Зафиксировано фактически наблюдаемое (что видно на экране, были ли ошибки в консоли). Непроведённые проверки помечаются как непроведённые. Скриншоты и `browser-verify` — опционально.

## 5. Ограничения

- Использовать существующие фреймворк, npm, скрипты и тестовый стек.
- Не переписывать несвязанный код и конфигурацию (допустима замена шаблонного содержимого `App.tsx` в рамках задачи).
- Не добавлять функциональность за пределами описанного сценария.
- Честно сообщать о невыполненном поведении.

## 6. Не входит в задачу (non-goals)

Детали сессии, drawer'ы, deep links; поиск и несколько фильтров; пагинация; полный API-контракт и матрица сценариев; наборы скриншотов desktop/mobile; исчерпывающая проверка адаптивности и доступности; полное покрытие тестами; CI, деплой, публичный URL; строгая миграция TypeScript и несвязанный рефакторинг; редактирование и удаление сессий; персистентность между перезагрузками (если не решено иначе в OQ-6).

## 7. Допущения (требуют подтверждения, не являются фактами)

- **A-1** Модель сессии минимальна: `id`, `title`, `status` (`scheduled` | `completed` | `cancelled`, см. D-1), `startsAt` (дата-время). Набор статусов подтверждён; имена полей остаются допущением.
- **A-2** Время вводится и отображается в локальном часовом поясе браузера; «в будущем» сравнивается с текущим временем клиента на момент отправки.
- **A-3** Язык интерфейса — английский (по формулировкам TASK.md: `All`).
- **A-4** Ошибку создания достаточно показать простым сообщением в форме; отдельный «восстановимый» сценарий требуется только для загрузки списка.
- **A-5** Форма может быть inline-блоком или отдельной панелью — визуальное решение за реализацией/`ui-designer`, не за требованиями.

## 8. Принятые решения

| ID | Решение | Закрывает | Влияет на |
|---|---|---|---|
| D-1 | Статусы сессий: `scheduled`, `completed`, `cancelled`. Варианты фильтра: `All` и `Scheduled`. | OQ-1 | AC-2.1–2.3, A-1 |
| D-2 | Новая сессия всегда получает статус `scheduled`; статус выставляет мок-API. В форме только название и дата/время. | OQ-2 | AC-3.2, AC-4.3, AC-5.6 |
| D-3 | Отдельной логики «невидимости» нет: созданная сессия имеет статус `scheduled` и потому видна и при `All`, и при `Scheduled`. Сброс фильтра не требуется. | OQ-3 (следует из D-1/D-2) | AC-4.4 |
| D-4 | В исходных мок-данных есть сессии всех трёх статусов. | Пожелание продукта | AC-5.5 |

## 10. Пробелы, требующие специалистов

- **API-контракт** (эндпоинты, форма payload/ответа, коды ошибок мока) → `api-integration`.
- **Архитектура** (механизм моков, расположение HTTP-клиента, владение состоянием списка) → `architect`.
- **Визуальное решение** (форма inline/модально, вид фильтра, состояния loading/error/empty) → `ui-designer` (опционально для учебного объёма).

## 11. Готовность

**Готово к планированию.** Блокирующие вопросы OQ-1 и OQ-2 закрыты решениями D-1 и D-2, OQ-3 закрыт решением D-3. Оставшиеся вопросы (OQ-4…OQ-10) не блокируют работу: на каждый есть допущение по умолчанию, их можно уточнить на этапе плана.

**Рекомендованный следующий шаг:** `writing-plans`. Выбор механизма моков (OQ-7) можно предварительно отдать `api-integration`/`architect` или решить прямо в плане.
