### Minor

**m-1. Невалидная дата от API роняет весь UI**
- **Где:** [src/App.tsx:139](../../src/App.tsx#L139), [src/api/sessionsClient.ts:18](../../src/api/sessionsClient.ts#L18), [src/mocks/sessionsMock.ts:98](../../src/mocks/sessionsMock.ts#L98)
- **Проблема:** `isSession` проверяет только, что `startsAt` — строка. `Intl.DateTimeFormat#format(new Date(''))` бросает `RangeError: Invalid time value`, а error boundary нет, поэтому рендер падает и приложение показывает пустой экран.
- **Сценарий:** мок на `POST` без `startsAt` возвращает `startsAt: ''`. То же произойдёт, если настоящий backend пришлёт некорректную дату. Сессия попадает в список, и весь `App` размонтируется.
- **Реальность риска:** через текущий UI сценарий недостижим, потому что форма всегда шлёт валидный ISO. Риск возникает при замене границы на настоящий backend.
- **Связь:** AC-1.3, AC-1.4 (ошибка должна быть понятной, а не пустым экраном), шаг 1 плана.
- **Возможное исправление:** в `isSession` проверять `!Number.isNaN(Date.parse(startsAt))`. Тогда клиент бросит ошибку, и UI уйдёт в штатное состояние ошибки.

**m-2. Хелпер теста завязан на CSS-класс**
- **Где:** [src/test/sessions-workspace.test.tsx:22](../../src/test/sessions-workspace.test.tsx#L22)
- **Проблема:** `visibleTitles()` ищет названия через `item.querySelector('.session-title')`. Это деталь разметки, а не роль или текст.
- **Сценарий:** при переименовании класса или изменении вёрстки тесты фильтрации и создания упадут, хотя поведение не изменилось.
- **Связь:** AC-6.2 («взаимодействует через UI (роли/тексты)»). Требование выполнено частично: клики и поиск идут по ролям, а утверждения о составе списка — через селектор класса.
- **Возможное исправление:** сравнивать состав списка через `within(item).getByText(...)` или по `textContent` элемента списка.

**m-3. Логика `?fail=1` с учётом StrictMode не покрыта автотестом**
- **Где:** [src/main.tsx:11-12](../../src/main.tsx#L11-L12)
- **Проблема:** `failListRequests = DEV ? 2 : 1` построено на допущении, что в dev ровно два стартовых `GET`. Тесты рендерят `App` без `StrictMode`, поэтому эта ветка проверяется только вручную.
- **Анализ кода:** логика верна. Оба смонтированных эффекта получают `500`, отброшенный результат игнорируется через `ignore`, `Retry` вызывает один `GET` и получает `200`.
- **Связь:** AC-1.4, AC-1.5, AC-5.4, шаг 5 плана. План сам относит эту проверку к ручной.
- **Что сделать:** изменение кода не требуется. Обязательно пройти ручной сценарий `?fail=1` → ошибка → `Retry` → список в шаге 7 и записать результат в `workflow-log.md`.
